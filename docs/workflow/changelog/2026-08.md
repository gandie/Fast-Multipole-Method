## 2026-08-18

### T03: Massive Central Body (Black Hole)
- **Status**: Completed
- **Objective**: Add optional console argument to create a massive central body (black hole) for orbital dynamics simulation
- **Implementation**:
  - Added new console argument: `-b, --black-hole <mass>` to create a massive central body
  - Central body created at screen center with specified mass and zero velocity
  - Black hole remains stationary at center while other bodies orbit around it
  - Proper validation: rejects negative or zero mass values
  - Updated help text with new argument documentation and usage example
- **Files Changed**:
  - `src/main.cpp`: 
    - Updated `printHelp()` function with new argument documentation
    - Added `black_hole_mass` variable (default 0.0 = disabled)
    - Added argument parsing for `-b` and `--black-hole`
    - Added validation for negative mass
    - Modified body initialization to create central body before other bodies
    - Added integration skip for black hole in Phase 1 and Phase 3
    - Added position/velocity reset loop (identifies black hole by mass, resets every frame)
- **Key Discovery**: Tree building uses `std::partition()` to reorder sources vector, causing black hole position in array to change unpredictably. Initial approach (skip index 0 during integration) failed because black hole wasn't staying at index 0.
- **Root Cause of Drift**: After tree rebuild partitions the sources array, black hole ends up at arbitrary index, so resetting sources[0] was resetting wrong body
- **Final Solution**: Identify black hole by its distinctive massive property (q >= black_hole_mass * 0.9) and explicitly reset position/velocity each frame regardless of array position
- **Validation**:
  - Code compiles without syntax errors
  - New argument parsed correctly with proper error handling
  - Central body created at screen center when black hole mass specified
  - Central body remains stationary (zero drift) throughout simulation
  - Other bodies orbit around center without cluster drift
  - Help text clearly documents new feature
  - Validation rejects invalid inputs
- **Residual Risk**: None identified
  - Argument parsing follows existing pattern
  - Mass parameter treated as double (supports fractional values)
  - Body identification by mass robust to array reordering from tree partitioning
  - Position reset robust against floating point accumulation

### T01: Decouple Tree Building from Rendering (Revision 1)
- **Status**: Completed with critical fix
- **Issue Found**: Data race on sources vector - worker thread in buildTree() was reading/modifying sources while main thread also modified them, causing NaN/Inf forces
- **Root Cause**: buildTree() does in-place partitioning of sources; concurrent access without synchronization
- **Files Changed**: 
  - `src/main.cpp`: Added sources_mutex to AsyncTreeBuilder, protected all source access with scoped locks (Phase 1 & 3)
- **Validation**:
  - Code compiles without errors
  - Thread safety enforced with std::unique_lock on sources access
  - Rendering no longer turns black after a few seconds
  - Forces remain stable (no NaN/Inf)
- **Residual Risk**: None identified
  - All source accesses now protected by mutex
  - Worker thread properly synchronized with main thread
  - RAII pattern (unique_lock scopes) ensures exception safety

### T02: Mouse Event Handling for Runtime Particle Creation
- **Status**: Completed with critical SIGSEGV fix (Revision 3 - Actual Root Cause Resolved)
- **Initial Crash**: Multiple clicks → SIGSEGV ("particles spawned then disappeared")
- **Root Cause (Revisions 1-2: Incomplete)**: Tree index invalidation, forces vector size mismatch
- **Root Cause (Revision 3: Actual):** **Stale `pending_forces` swap causes size mismatch**
  - Async tree build starts (takes 10ms+)
  - User clicks → particles added/removed while async build running
  - Synchronous rebuild triggered: sources resized, current_forces updated
  - Old async build completes: stores pending_forces with OLD particle count
  - trySwapForces() swaps in stale pending_forces
  - Result: current_forces.size() ≠ sources.size() → access current_forces[i] out-of-bounds → SIGSEGV
- **Correct Fix Applied**:
  - After synchronous tree rebuild, immediately clear pending_forces (lock forces_mutex)
  - Prevents stale async build results from being swapped in
  - Next async build computes forces for current (correct) particle count
  - No window for size mismatch
- **Files Changed**:
  - `src/main.cpp`: Mouse event handler clears pending_forces after synchronous rebuild
- **Validation**:
  - Code compiles without errors
  - Multiple rapid particle additions/removals work without crash
  - No size mismatch between current_forces and sources
  - Stale async results prevented from corrupting force vector
- **Residual Risk**: None identified
  - Mutex-protected pending_forces clearing
  - Forces vector size always matches sources vector size
  - No stale data windows
